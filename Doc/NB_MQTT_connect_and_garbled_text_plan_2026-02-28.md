# NB-IoT 云连接失败与串口乱码问题说明（评审版）

日期：2026-02-28  
状态：仅文档说明，未执行本轮代码修改

## 1. 现象

根据现场日志：

- 模块初始化成功：`[EC01G] Init OK`
- SIM 检查成功：`[EC01G] SIM card OK`
- 网络注册成功：`[NB] Network registered`
- 在 MQTT 连接阶段出现：
  - `Timeout waiting 'OK'`
  - 同时又出现 `+ECMTCONN: 0,0,0`
  - 最终被判定为 `MQTT connect failed`
- 之后系统进入 STOP2 并能按 5 秒唤醒：`[APP] Wakeup reason=1`

## 2. 问题定位

### 问题A：云连接失败（实为判定逻辑误判）

`+ECMTCONN: 0,0,0` 是 MQTT 连接成功 URC，但当前流程先硬等 `OK`。  
一旦 `OK` 受串口噪声/乱码影响未被匹配，就提前判失败，即使后续已出现成功 URC。

### 问题B：串口打印乱码

日志存在异常字符（如 `O媴`），说明 AT 文本链路存在偶发字符污染。  
这会直接影响基于纯字符串匹配（如 `"OK"`）的状态判断。

### 结论

当前“连接失败”主要是**判定策略脆弱**，不完全是“真正未连接上云”。

## 3. 可能原因

1. AT 命令回显开启（默认回显），接收缓存里回显+URC+响应混在一起。  
2. 串口偶发 FE/NE/ORE 错误导致个别字符损坏。  
3. 代码将 `OK` 作为强制成功条件，但在 EC01G 的 MQTT 连接场景中，关键应以 `+ECMTCONN` 结果为准。

## 4. 解决方案

## 4.1 协议判定改造（核心）

将 MQTT 连接成功判定改为：  
**以 `+ECMTCONN: 0,0,0` 为主判定条件**，`OK` 仅作辅助信息，不再作为唯一门槛。

建议处理逻辑：

1. 发送 `AT+ECMTCONN...`
2. 等待一段时间接收 URC
3. 若收到 `+ECMTCONN: 0,0,0` => 成功
4. 若收到 `+ECMTCONN` 但 result 非 0 => 明确失败
5. 超时才判失败

## 4.2 降低乱码干扰

1. 在初始化阶段执行 `ATE0` 关闭回显。  
2. 串口错误统计：记录 FE/NE/ORE 计数，便于定位是否是物理链路问题。  
3. 超时日志同时输出 ASCII 与 HEX（排查字符被污染场景）。

## 4.3 重试策略优化

连接失败后先做快速链路探测（如 `AT`），再重试 `ECMTCONN`，减少误判导致的整轮失败。

## 5. 验证方案

1. 连续运行 20 轮上报，统计：
   - `ECMTCONN` 成功率
   - “OK超时但URC成功”出现次数（应降为 0）
2. 对比 `ATE0` 前后乱码频次。  
3. 检查串口 FE/NE/ORE 计数是否持续增长。  
4. 保持 STOP2 5 秒唤醒回归验证（确认本问题改动不影响低功耗链路）。

## 6. 预期结果

1. 消除“已连上却被判失败”的假失败。  
2. 明显降低日志乱码对流程判断的影响。  
3. 云上报成功率提升，重试次数下降。  
4. STOP2 周期唤醒保持稳定。
